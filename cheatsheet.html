01b🧩 Carpeta de skills válida▼

Cualquier profundidad sirve; se detecta cada SKILL.md.

tree
~/code/agents/plugins/
├── python-dev/skills/fastapi-templates/SKILL.md
├── react-dev-suite/skills/react-architecture/SKILL.md
└── ai-dev/skills/langgraph-core/SKILL.md
⚡ Cada SKILL.md necesita name: y description: en su encabezado.
⚠️ De un plugin solo se usan las skills; los subagentes, comandos y hooks son propios de Claude Code.
02📦 Instalación una vez por máquina▼
bash
# 1. Requisitos
node --version                 # 20.19 o superior
npm install -g @fission-ai/openspec@latest

# 2. El arnés
git clone <url-del-arnés> ~/.specboot
cd ~/.specboot && npm link     # deja disponible `specboot`

# 3. Tus skills
specboot source add ~/code/agents/plugins
specboot source list

# 4. Enlazar todo para los cuatro agentes
specboot install

# 5. Verificar
specboot doctor

Después, en Cursor: Settings → Rules → User Rules, y pega el texto que specboot install mostró al final.

⚡ Repite specboot install cada vez que actualices OpenSpec, el arnés o tus skills.
03🌱 Flujo greenfield proyecto nuevo▼
bash
# 1. Repositorio vacío del cliente
mkdir mi-proyecto && cd mi-proyecto && git init
git commit --allow-empty -m "chore: init"

# 2. Iniciar con un preset de frentes
specboot init <cliente> \
  --fronts ~/.specboot/presets/fronts.fastapi-react.json \
  --remote <url-git-privada-de-specs>

# 3. Registrar tu documento de arquitectura (opcional, manda sobre las skills)
specboot doc add ~/ruta/arquitectura.md
specboot doc add ~/ruta/backend.md --front backend

# 4. Comprobar
specboot doctor
Luego, con el agente
#Qué le pides al agenteResultado
0«Ejecuta la skill specboot-plan»Ideación, PRD, historias y backlog en docs/planning/
1«Ejecuta la skill specboot-prescribe»Lee overrides, documentos y skills base; te pregunta solo lo que ningún documento cierra; escribe openspec/standards/
2Revisas y corriges lo marcado [assumed]Pones status: reviewed en cada documento
3«Propón el cambio del esqueleto del proyecto»Cambio de OpenSpec con carpetas, linter, pruebas y CI
4«Aplica el cambio»Código del esqueleto
5specboot checkTodos los checks activos pasan
6Commit del esqueleto en el repositorio del cliente
7Traspaso: «Ejecuta la skill specboot-map» y después specboot mode brownfieldLo prescrito se verifica contra el código
8specboot sync -m "standards: verify, switch to brownfield"Store versionado
⚠️ specboot map y specboot doctor avisan «handoff due» cuando toca el paso 7. No empieces otro cambio antes.

04🏗️ Flujo brownfield proyecto existente▼
bash
cd proyecto-existente

# 1. Iniciar (detecta solo que hay código)
specboot init <cliente> --remote <url-git-privada-de-specs>

# 2. docs/ queda local e ignorada por defecto. Solo si el cliente debe verla:
specboot docs client

# 3. Opcional: documento de arquitectura objetivo y frentes
specboot doc add ~/ruta/arquitectura.md
#   edita openspec/standards/fronts.json si quieres skills por frente

# 4. Comprobar
specboot doctor
specboot check --list   # comandos de lint y pruebas que encontró en el proyecto
Luego, con el agente
#Qué le pides al agenteResultado
1«Ejecuta la skill specboot-map»Lee reglas, configuración y código; escribe openspec/standards/ con evidencia por regla
2Revisas lo marcado [assumed] y las desviaciones frente a tu documentoPones status: reviewed
3specboot checkLínea base: anota en los estándares qué fallaba antes de tocar nada
4specboot sync -m "standards: map project"Store versionado
⚡ En un proyecto existente el código manda. Tu documento describe el objetivo; las contradicciones se reportan y tú decides.
11⚖️ Orden de autoridad▼
  1. Reglas de agentes que el cliente ya versiona.
  2. Tus documentos de arquitectura, corregidos por overrides.md.
  3. decisions.md.
  4. El código (existente) o las skills base (nuevo).
  5. Skills genéricas.
05🔁 Ciclo de cada cambio ambos flujos▼
producto, épica o funcionalidad grande→specboot-plan·una historia→enrich-us·un cambio pequeño→directo
PasoSkill o comando
Afinar la historia (opcional)enrich-us
Proponeropenspec-propose
Implementaropenspec-apply-change
Verificarspecboot check
Revisar, en una sesión nuevaadversarial-review
Refrescar estándares si cambiaron carpetas, rutas, nombres o idiomaspecboot-map, más filas en overrides.md
Archivaropenspec-archive-change
Versionar specs y traer los del equipospecboot sync -m "..."
Commit del códigogit add <archivos> y git commit, nunca git add -A

Cómo invocar una skill: /nombre en Claude Code, Cursor y opencode; $nombre en Codex; o pídelo en lenguaje natural.

10👥 Compartir con el equipo▼
Tú, una vez
bash
git -C ~/.specboot-data/stores/<cliente> \
  remote add origin <url-privada>
specboot sync
Cada compañero, una vez

Instala el arnés, clona tu repositorio de skills, specboot source add e install, y en su clon del repositorio del cliente:

bash
specboot init <cliente> --remote <url-privada>
⚡ Día a día: specboot pull al empezar, specboot sync -m "..." al terminar. doctor avisa si vas por detrás o si tus skills no están en el commit del proyecto.
06🧱 fronts.json de referencia▼

Ruta: <proyecto>/openspec/standards/fronts.json

json
{
  "mode": "greenfield",
  "docs": { "placement": "local" },
  "planning": {
    "skills": ["product-ideation-brainstorm", "breakdown-feature-prd", "project-manager"],
    "output": "docs/planning"
  },
  "fronts": {
    "backend": {
      "path": "backend",
      "core": ["python-project-structure", "fastapi-templates", "python-code-style", "python-testing-patterns"],
      "topics": ["python-observability", "langgraph-fundamentals", "rag-implementation"],
      "decisions": { "architecture": "monolito modular" },
      "checks": ["uv run ruff check .", "uv run mypy .", "uv run pytest"]
    },
    "frontend": {
      "path": "frontend",
      "core": ["react-architecture", "react-core", "react-testing"],
      "topics": ["react-state", "react-forms"],
      "decisions": { "architecture": "Screaming (feature-first)" },
      "checks": ["npm run lint", "npm run typecheck", "npm run test -- --run"]
    }
  }
}
CampoRegla
core3 a 5 skills que definen estructura, estilo y pruebas. Usa el name de la skill, no el de su carpeta
topicsSkills que se cargan solo cuando la tarea las necesita
decisionsLo ya decidido; el agente no lo vuelve a preguntar
checksEscritos como se ejecutan de verdad (uv run ..., pnpm run ...)
planningSkills del plugin plan. Las añade specboot map en cuanto están instaladas; escribe tu propia lista para fijarla, o {"disabled": true} para apagarla
⚡ Después de editarlo: specboot map.
07🗂️ Qué hay en openspec/standards/▼
ArchivoEditas túNotas
fronts.jsonSíFrentes, modo, ubicación de docs/
checks.jsonSolo para añadir comandos propios o desactivar con "disabled": trueLos de los frentes se editan en fronts.json
overrides.mdSí«Término del documento → identificador a usar»
decisions.mdSíDecisiones cerradas y elementos aplazados
*-standards.md, development-guide.md, data-model.md, api-spec.mdRevisas y pones status: reviewedLos escribe el agente
skill-gaps.mdNoLo que tus skills no cubrieron
project-facts.md, fronts.lock.jsonNoSe regeneran con specboot map
08⌨️ Comandos▼
ComandoPara qué
specboot doctor [--strict]Qué falta o está mal, con el comando que lo arregla
specboot source add <carpeta>Registrar tus skills
specboot installEnlazar skills y regla global
specboot init <cliente> [opciones]Preparar un proyecto
specboot docs local|client|storeDónde vive docs/
specboot doc add <archivo> [--front <f>]Registrar un documento de arquitectura
specboot map [--accept]Regenerar inventario y sincronizar checks
specboot check [--list] [--strict]Ejecutar o listar los checks
specboot mode brownfieldCerrar la fase de proyecto nuevo
specboot linkRecrear enlaces en un worktree nuevo
specboot sync -m "..."Confirmar, traer lo del equipo y subir
specboot pullTraer lo del equipo sin subir

Opciones de init: --remote <url>, --fronts <archivo>, --new, --existing, --docs local|client|store, --gitignore.
